ตั้งค่า Google Workspace และ OAuth

คู่มือสำหรับเจ้าของแอปในการเตรียม Google Cloud ให้ผู้ใช้เชื่อมต่อบัญชีของตนเองกับ Google Sheets, Google Drive และ Google Calendar

รูปแบบการใช้งาน: เจ้าของแอปตั้งค่า OAuth Client และใส่ Client ID ในระบบ build/deployment เพียงครั้งเดียว ผู้ใช้ทั่วไปกด “เชื่อมต่อ Google” เลือกบัญชีของตน และอนุญาตสิทธิ์ได้ทันที ผู้ใช้ไม่ต้องสร้าง คัดลอก หรือกรอก Client ID และไม่ต้องใช้บัญชี Google ของเจ้าของแอปร่วมกัน

1. เตรียม Google Cloud project (เจ้าของแอป)

  1. เปิด Google Cloud Console แล้วเลือกหรือสร้างโปรเจกต์ที่เจ้าของแอปควบคุม
  2. เปิด Google Calendar API, Google Sheets API และ Google Drive API เฉพาะบริการที่แอปเปิดให้ใช้
  3. เปิด Google People API เฉพาะเมื่อมีฟีเจอร์โอนย้ายรายชื่อผู้ติดต่อ
  4. ตั้งค่า OAuth consent screen: ชื่อแอป อีเมลสนับสนุน โดเมนที่ได้รับอนุญาต นโยบายความเป็นส่วนตัว เงื่อนไขการใช้งาน และผู้ติดต่อสำหรับนักพัฒนา

2. สร้าง OAuth Client แยกตามแพลตฟอร์ม

  1. ไปที่ APIs & Services → Credentials แล้วสร้าง OAuth Client ตามชนิดแพลตฟอร์มที่แอปรองรับ
  2. Web: เพิ่ม Authorized JavaScript origins ให้ตรงกับโดเมน production และ development จริง รวมถึง protocol และ port
  3. Android: กำหนด package name และ SHA certificate fingerprints ของ signing key ที่ใช้จริง
  4. iOS: กำหนด bundle identifier, iOS Client ID และ reversed-client-ID URL scheme ให้ตรงกับแอป
  5. macOS: กำหนด bundle identifier และ redirect configuration ตามวิธีที่แพ็กเกจรองรับ
  6. Windows/Linux: อย่าเปิดปุ่ม Google Sign-In จนกว่าจะมี native OAuth flow ที่รองรับและทดสอบ PKCE/state, redirect handling และ secure token storage ครบถ้วน

ใส่ public Client ID ผ่าน build/deployment configuration ของเจ้าของแอป เช่น Web ใช้ GOOGLE_WEB_CLIENT_ID และค่าที่เกี่ยวข้องตามแพลตฟอร์ม ห้ามให้ผู้ใช้ปลายทางกรอกค่าเหล่านี้

ข้อควรระวัง: Client ID เป็น public identifier แต่ Client Secret, access token, refresh token, service-account key และ private key เป็นข้อมูลลับ ห้ามฝังข้อมูลลับเหล่านี้ใน Flutter Web/mobile, source control หรือ artifact ที่เผยแพร่สู่ผู้ใช้

3. กำหนดสิทธิ์และการเผยแพร่ OAuth

  • ขอ scopes แบบ incremental เมื่อผู้ใช้เริ่มใช้ฟีเจอร์ที่ต้องการสิทธิ์นั้น ไม่ขอสิทธิ์ทั้งหมดตั้งแต่การเข้าสู่ระบบพื้นฐาน
  • อธิบายให้ชัดว่าการอนุญาตแต่ละ scope ใช้ทำอะไร และใช้สิทธิ์เท่าที่จำเป็น
  • OAuth consent screen ที่อยู่ในสถานะ Testing จำกัดการใช้งานไว้กับ test users ที่กำหนด ไม่ถือว่าพร้อมให้ผู้ใช้ทั่วไป
  • เจ้าของโปรเจกต์ต้อง Publish audience และดำเนินการ verification กับ Google สำหรับ sensitive/restricted scopes เมื่อมีข้อกำหนด

4. ประสบการณ์ของผู้ใช้และการแยกบัญชี

  • ผู้ใช้เห็นปุ่ม “เชื่อมต่อ Google” และสถานะบัญชีที่เชื่อมต่อ ไม่เห็นหน้ากรอก OAuth Client ID
  • ผู้ใช้แต่ละคนเลือกบัญชี Google ของตนเองและให้ consent ด้วยตนเอง
  • ทุกคำขอ Google API ต้องใช้ authorization ของบัญชีที่ผู้ใช้คนนั้นเลือก ห้ามใช้บัญชีเจ้าของแอปเป็นบัญชีกลาง
  • รองรับการปฏิเสธ consent, token/grant หมดอายุหรือถูก revoke, disconnect, sign-out และ reconnect
  • ไม่บันทึก token, credential หรือเนื้อหาตารางเวรส่วนบุคคลลง log
  • ทดสอบ account isolation และการซิงก์จริงด้วยบัญชีที่ไม่ใช่เจ้าของโปรเจกต์ ก่อนประกาศว่าพร้อมใช้งานสาธารณะ

5. ตรวจสอบและแก้ปัญหา

  • origin_mismatch: ตรวจ Authorized JavaScript origins ให้ตรงกับ URL จริงทุกตัวอักษร รวม protocol และ port
  • บัญชีเข้าสู่ระบบไม่ได้: ตรวจ Client ID ของแพลตฟอร์ม, package/bundle identifier, signing fingerprint, redirect configuration และ consent screen
  • ยังซิงก์ไม่ได้: ตรวจว่า API เปิดใช้งานและผู้ใช้อนุญาต scope ที่ฟีเจอร์นั้นต้องใช้แล้ว
  • บัญชีหนึ่งเห็นข้อมูลของอีกบัญชี: ให้หยุดการซิงก์ทันทีและตรวจ session/account binding ก่อนเปิดใช้งานต่อ

ดูรายละเอียดเชิงเทคนิคเพิ่มเติมได้ที่ Google Cloud and OAuth Setup และ คู่มือติดตั้งและใช้งาน

คู่มือนี้เป็นแนวทางการตั้งค่า ไม่ใช่หลักฐานว่า OAuth credentials, consent verification หรือการซิงก์ของบัญชีใดผ่านการทดสอบแล้ว การเปิดใช้งานจริงยังต้องผ่านการตรวจสอบตามแพลตฟอร์มและบัญชีผู้ใช้จริง
